# video-capture

Изолированный крейт записи видео экрана под Windows поверх `windows-capture` 2.0.1
(Media Foundation). Не интегрирован в `virshot`: root-крейт его не использует, это
самостоятельный path-dep крейт со своим публичным API.

Захват — только Windows. На Linux крейт компилируется (сборка-check) и прогоняет
pure-логику: весь capture-код и зависимость `windows-capture` находятся под
`#[cfg(windows)]`, и каждая capture-функция возвращает
`CaptureError::UnsupportedPlatform` ([`src/error.rs`](src/error.rs)). Linux-бэкенд
(GStreamer + VA-API) не делается.

`#![forbid(unsafe_code)]`: в коде крейта `unsafe` нет; `unsafe` внутри `windows-capture`
— дело третьей стороны и к этому правилу не относится.

Публичная поверхность: `config` (параметры кодирования, которые библиотека реально
может применить), `ring` (кольцевой буфер pre-roll), `error` (типизированные
ошибки), `engine` (capture-цикл, поток-писатель энкодера и фасад `Recorder`).

## Запуск демо на Windows

Тестовый egui-пример: [`examples/capture_demo.rs`](examples/capture_demo.rs).

```sh
# сборка под Windows-цель (cross-build из Linux/WSL, MinGW-w64)
cargo build --target x86_64-pc-windows-gnu --example capture_demo

# на Windows — прямой запуск
cargo run --example capture_demo
```

Внутри репозитория те же команды через обёртку кэша:
`./cargo.sh build --target x86_64-pc-windows-gnu -p video-capture --example capture_demo`
и `./cargo.sh run -p video-capture --example capture_demo`.

- Путь вывода по умолчанию: `%USERPROFILE%\Videos\test.mp4` (если `USERPROFILE` пуст
  или ОС не Windows — `test.mp4` рядом с текущей директорией). Поле «Output file»
  редактируется, родительская папка создаётся при нажатии «Запись».
- Кнопки: **«Запись»** — ставит команду `Start` в очередь **живой** сессии через
  `Recorder::start(path)`: capture-поток, кольцо и индикатор захвата Windows не
  пересоздаются, запись активируется на следующем захваченном кадре, а пре-ролл
  берётся из уже наполненного кольца и выгружается **отдельным потоком-писателем**
  (см. «Писатель энкодера: пре-ролл без фриза») — кнопка не ждёт ни энкодер, ни
  файл. Новая сессия создаётся только когда живой нет — или движок освободил её
  после «Стоп» с выключенным буфером или после выключения «Буфера» без записи (на
  освобождённой сессии `start` отвечает `CaptureError::NotConfigured`, и демо
  перестроит recorder) — и при галке debug-дампов: директория дампа задаётся в
  конструкторе, поэтому там `Recorder::with_debug_dump(cfg, Some(dir))` +
  `start(path)` (тот же pending-ack и та же активация на первом кадре); без дампов
  новая сессия — `Recorder::recording(cfg, path)`, где команда `Start` ставится в
  очередь **до** запуска capture-потока. Предыдущий recorder уничтожается (его
  `Drop` останавливает capture-поток, но **не ждёт** поток-писатель: незакрытый
  файл тот дописывает сам). **«Стоп»** — ставит команду завершения в очередь и
  сразу возвращает `Ok(())`: flush + mux делает поток-писатель, который по «Стоп»
  закрывает очередь живых кадров, дописывает queued-кадры и закрывает файл; кнопка
  активна только при активной записи; при кольце с ёмкостью > 0 захват продолжает
  работать и кольцо наполняется заново, при ёмкости 0 сессия освобождается
  (см. «Буфер 0 освобождает захват»). **«Буфер»** рядом с «Запись»/«Стоп» —
  переключает пре-ролл живой сессии
  (`Recorder::enable_replay(seconds)` / `disable_replay()`), а когда сессии нет —
  запускает сессию только под кольцо (`Recorder::new(cfg)`), файл при этом не
  пишется; при ползунке 0 сессия не запускается (кольцу нечего наполнять, кнопка
  disabled с подсказкой). Выключение «Буфера» без активной записи закрывает сессию
  на ближайшем доставленном кадре: индикатор гаснет, следующие команды отвечают
  `CaptureError::NotConfigured`, а «Буфер» или «Запись» поднимут новую. Кнопка
  показывает состояние, запрошенное фасадом
  (`replay_enabled()`); на Linux сессия не запускается, и под статусом лежит
  подсказка, что захват там не поддерживается.
- `start(path)` и `stop()` больше не блокируют поток: команда ложится в канал и
  возвращает `Ok(())` сразу. Результат читается в цикле UI —
  `poll_recording_ack()` / `poll_stop_ack()`: `None`, пока команда ожидает;
  `Some(Ok(()))`, когда ack пришёл («запись активна», «файл записан»); `Some(Err(..))`
  на ошибку команды или на таймаут 5 с без ack. Оба опроса вызываются на каждой
  итерации UI, и окно постоянно перекрашивается — иначе ack на статичном столе
  никогда не прочитается. Третьим опросом на той же итерации читается
  **освобождение сессии без очереди команд** — `Recorder::poll_session_release()`:
  выключение «Буфера» без записи не является ack'ом ни одной команды, поэтому
  именно этот опрос приносит `захват освобождён`; пока ack висит в очереди, он
  ничего не вычитывает (чтобы не съесть ack) и возвращает уже записанный флаг.
- Строка статуса: `ожидание`; `запуск записи… <path>` — команда в очереди, это ещё
  не запись; `запись активна: <path>`; `завершение, запись файла… <path>` — файл ещё
  не дописан; `захват активен, буфер N с (~X MiB)` или `захват активен, буфер
  выключен`; `файл записан: <path>, захват активен, буфер …; кольцо наполняется
  заново`; `файл записан: <path>, захват освобождён (буфер выключен)` — сессия
  захвата закрыта при выключенном кольце: это либо «Стоп» с выключенным буфером,
  либо выключение «Буфера» без записи; следующая «Запись» или «Буфер» поднимет
  новую; `ошибка: <текст
  CaptureError>`. Строки `idle` и `capturing (replay armed)` из прежней версии
  больше не появляются, и буфер не анонсится при replay = 0.
- Параметры в логах: при «Запись» одной строкой печатаются все выбранные параметры
  (`config_dump`: codec, битрейт (CBR — режимов rate-control в API нет), разрешение,
  фильтр масштабирования, fps, replay, audio — неподдерживаемые помечены
  `(unsupported …)`), плюс строка engine с `native=… target=… scaled=…
  scale_filter=…`.
- Логи: INFO и выше → stdout, WARN и выше → stderr; уровень задаётся `RUST_LOG`
  (по умолчанию `info`). Пример на Linux тоже открывается (например под
  `xvfb-run -a`) и показывает `error: screen capture is Windows-only…`.
- Debug-дампы: галка **«Debug: dump кадров в .tmp/dumps»** (или переменная
  окружения `VC_DEBUG_DUMP_DIR`) пишет первые 3 кадра raw-buffer-пути —
  `frame_<n>_raw.png` (ровно байты, поданные в энкодер; в просмотрщике они
  перевёрнуты), `frame_<n>_flipped.png` (то, как должен выглядеть кадр) и
  `frame_<n>_rgba.png` (те же байты как RGB — проверка каналов). Дампы пишутся
  только во время записи, и при записи **каждый** кадр идёт raw-buffer путём
  (GPU-путь не используется — см. «Писатель энкодера: пре-ролл без фриза»),
  поэтому первые дампы покрывают первые записанные кадры при любом размере кадра,
  включая совпадающий с целевым; отказ дампа — только warn, захват не ломается.

## Параметры и их статус

Статусы повторяют feasibility-таблицу спеки
(`.dumbspec/current/2026-11-07_video-capture-crate/spec.md`), без workaround'ов.

| параметр | значения | статус |
| --- | --- | --- |
| codec | `h.264`, `HEVC (h.265)` | реализовано — `VideoSettingsSubType::H264` / `HEVC`; отдельного значения «h.265» в API нет, это alias для HEVC |
| битрейт | kbps: в демо 500…50 000, по умолчанию 15 000 | реализовано — `VideoSettingsBuilder::bitrate(bps)` (MF `MF_MT_AVG_BITRATE`), целевой CBR; единственный rate-control в библиотеке, режимов качества в API нет (см. «Ограничения и риски») |
| разрешение | `Resolution::Height(u16)` — произвольная высота от 1 пикселя (`Height(160)`; `P720`/`P1080` — те же `Height(720)`/`Height(1080)`), `Full` = нативный размер монитора; по умолчанию `P1080` | реализовано — высота фиксируется, ширина выводится из пропорций экрана (`native_w * h / native_h`, floor, ≥ 1) одним масштабом по обеим осям, `label()` → `"160p"`/`"Full"`; при высоте выше нативной остаётся нативный размер (апскейл не делается); `Height(0)` недопустима и отвергается конструкторами (`CaptureError::NotConfigured`); CPU-resize BGRA-кадра на каждый кадр (библиотека только кропает/чёрно-падит, не ресемплирует), подача через `send_frame_buffer` |
| фильтр масштабирования | `Nearest`, `Bilinear` (по умолчанию), `CatmullRom`, `Gaussian`, `Lanczos3` | реализовано — `scale_filter` в `CaptureConfig`, используется только когда размер кадра ≠ целевой; `Nearest`/`Bilinear` — свои kernel'ы креита, остальные — `image::imageops::resize` (см. «Масштабирование и фильтры», замерены) |
| fps | `u8` от 1 (в демо 1…60, по умолчанию 30) | реализовано как минимальный интервал обновления + pacing: `frame_rate(u32::from(fps))` (знаменатель 1) и `MinimumUpdateIntervalSettings::Custom(1/fps)` — только hint, константный rate API не гарантирует; кадры pacing-ятся по timestamp (`should_send`), кадры с более ранним timestamp (джог часов) отбрасываются; `fps = 0` недопустим и отвергается конструкторами |
| replay_buffer | 0…600 сек (клемп `CaptureConfig::replay_seconds()`) | реализовано — кольцевой буфер BGRA-кадров в памяти; capture-поток копает кадры с момента `Recorder::new`, при старте записи первые кадры mp4 = последние N секунд до старта, дальше live-запись до «Стоп»; включается и выключается в рантайме (`enable_replay` / `disable_replay`) |
| replay в сжатом виде | H.264/HEVC-пакеты в памяти вместо raw BGRA-кадров | **не реализовано — не получается сделать средствами библиотеки**: входной дескриптор энкодера жёстко `VideoEncodingProperties::CreateUncompressed(Bgra8)` (`windows-capture` `encoder.rs:882-887`), `VideoEncoder` принимает только `send_frame` (DirectX-поверхность) и `send_frame_buffer` (raw байты), сжатые байты наружу не отдаются (output-сторона — `transcode.TranscodeAsync()` с ожиданием, пишет в stream или файл), `new_from_stream(..., IRandomAccessStream)` пишет in-memory stream без truncation и без API для чтения packets; прямой dep `windows` + собственный COM-stream потребовал бы `unsafe` (`#![forbid(unsafe_code)`) и отдельного согласия пользователя. Кольцо остаётся сырым BGRA; единственные способы экономии RAM — буфер на **целевом** размере энкодера (уже сделано), меньшее разрешение (`720p`) и меньшее число секунд |
| audio | `none`, `system`, `mic`, `both` | `none` — реализовано (`AudioSettingsBuilder::default().disabled(true)`); `system` / `mic` / `both` — **не реализовано**: `windows-capture` принимает аудио-поток, но не захватывает источник (нет loopback/WASAPI и нет микрофона); заглушка остаётся в API, решение по аудио за пользователем |

То, что библиотека может запросить, но не применяет, помечено в API флагом
`AudioMode::is_supported()` и показано в UI disabled, а не «тихо принято».
Нерабочие опции удалены из API целиком (spec v5): выбор энкодера и режимы
битрейта — см. «Ограничения и риски».

## Формат вывода

Только **mp4**: контейнер фиксирован (MPEG4, `ContainerSettingsBuilder::default()`),
muxing делает Media Foundation. MKV/WebM вне scope.

## Масштабирование и фильтры

Разрешение задаёт **высоту** — произвольную (`Resolution::Height(u16)`, хоть
`Height(160)`); ширина считается из пропорций экрана одним масштабом по обеим
осям (`Resolution::target_size(native)`: `native_w * h / native_h`, floor, ≥ 1),
апскейл не делается. На экране 1680×1050: `Height(720)` → **1152×720** (`label()`
→ `"720p"`), `Height(1080)` → нативный 1680×1050 (нативная высота меньше 1080),
`Full` → нативный размер; на 16:9 экране 1920×1080 `Height(160)` → **284×160**
(`label()` → `"160p"`). `Height(0)` не имеет целевого размера и отвергается
конструкторами до захвата.

Ресайз выполняется на CPU (`engine::resize_bgra`) только когда размер кадра ≠
целевой. При совпадении размеров ресайза нет, и `scale_filter` ни на что не
влияет. GPU-путь `send_frame` при записи **не используется** (`Frame` не `Send`),
поэтому каждый записанный кадр — CPU-копия байтов, а не поверхность: ресайз при
несовпадении размеров плюс переворот строк, и переворот применяется даже когда
размер совпадает с целевым.

Замеры (release-сборка, Linux-хост, 1680×1050 → 1152×720, steady-state):

| фильтр | kernel | мс/кадр | что даёт |
| --- | --- | --- | --- |
| `Nearest` | свой | ≈ 4.6 | самый дешёвый, но тонкие штрихи шрифта при даунскейле теряются |
| `Bilinear` (по умолчанию) | свой (separable, целые веса 0…256) | ≈ 10.1 | штрихи сохраняются, лёгкий блюр; влезает в бюджет 33.3 мс при 30 fps |
| `CatmullRom` | `image` | ≈ 148 | резче bilinear, но это ~7 fps на CPU |
| `Gaussian` | `image` | ≈ 207 | гладче, но это ~5 fps на CPU |
| `Lanczos3` | `image` | ≈ 198 | самый резкий даунскейл, но это ~5 fps на CPU |

`Nearest` и `Bilinear` — kernel'ы самого креита: `image::imageops::resize` на том
же даунскейле стоит ≈ 52 мс даже для `Nearest` и ≈ 78 мс для bilinear-интерполяции,
т.е. даже самый дешёвый чужой kernel не влезает в 30 fps. `image`-фильтры
(`CatmullRom`/`Gaussian`/`Lanczos3`) оставлены как опции качества — честно, с их
ценой; чужих kernel'ов для `Nearest`/`Bilinear` в API нет.

Переворот строк (`flip_rows_bgra`, см. «Ориентация кадров») стоит ≈ 0.5 мс на
кадр 1280×720 и входит в тот же raw-buffer-путь.

## Оценка памяти replay-буфера

Формула `ring::estimated_memory_bytes(seconds, fps, width, height)`:

```
байты = w * h * 4 * fps * seconds
```

вычисляется на насыщающей арифметике (`saturating_mul` на каждом шаге), поэтому
экстремальные параметры не переполняют `usize`, а насыщаются до `usize::MAX`.
`w`/`h` — целевой размер `Resolution::target_size(native)`: произвольная выбранная
высота и пропорциональная ей ширина, либо нативный размер монитора, когда он
меньше запрошенной высоты по высоте или выбран `Full`. Таблица посчитана для
подсказки 1920×1080 (это 16:9, поэтому `Height(720)` даёт ровно 1280×720); на
16:10 экране 1680×1050 кадр `Height(720)` = 1152×720 = 3.31 MiB, т.е. памяти чуть
меньше.

| размер кадра | fps | секунд | кадров | память |
| --- | --- | --- | --- | --- |
| 1920×1080 (7.91 MiB/кадр) | 30 | 30 | 900 | ≈ 7.0 GiB |
| 1920×1080 | 30 | 60 | 1 800 | ≈ 13.9 GiB |
| 1920×1080 | 30 | 600 | 18 000 | ≈ 139.0 GiB |
| 1920×1080 | 60 | 600 | 36 000 | ≈ 278.1 GiB |
| 1280×720 (3.52 MiB/кадр) | 30 | 30 | 900 | ≈ 3.1 GiB |
| 1280×720 | 30 | 600 | 18 000 | ≈ 61.8 GiB |
| 1280×720 | 60 | 600 | 36 000 | ≈ 123.6 GiB |

Буфер вытесняет старейшие кадры при переполнении, но верхняя граница — таблица выше:
600 секунд на 1080p/60fps — это ~278 GiB, а не «несколько ГБ». В демо оценка
выводится подписью под слайдером в MiB и считается по подсказке 1920×1080 (реальный
размер монитора известен только внутри engine на Windows).

Кольцо хранит **сырые BGRA**, поэтому размер буфера в памяти и размер записанного
файла различаются на порядок — арифметика по формуле выше, 10 секунд @30 fps =
300 кадров:

- `Height(720)`: на экране 1920×1080 кадр 1280×720 = 3 686 400 Б →
  300 × 3 686 400 = 1 105 920 000 Б ≈ **1.03 GiB** RAM; на 1680×1050 кадр
  1152×720 = 3 317 760 Б → 995 328 000 Б ≈ **0.93 GiB**.
- `Full` (и `Height(1080)`, когда нативная высота ≥ 1080): на 1920×1080 кадр
  1920×1080 = 8 294 400 Б → 2 488 320 000 Б ≈ **2.32 GiB**; на 1680×1050
  нативная высота 1050 < 1080, поэтому `Full` и `Height(1080)` дают нативный
  1680×1050 = 7 056 000 Б/кадр → 2 116 800 000 Б ≈ **1.97 GiB** (апскейла нет).
- Маленькая произвольная высота: `Height(160)` на 1920×1080 — ширина
  `1920 · 160 / 1080 = 284.44` → floor **284**, кадр 284×160 = 181 760 Б
  (≈ 0.17 MiB); 10 с @30 fps → 300 × 181 760 = 54 528 000 Б ≈ **52.0 MiB**.

Тот же 10-секундный отрезок в mp4 при `bitrate_kbps = 15 000`: 15 000 kbps ×
10 с = 150 000 килобит = 18 750 000 Б ≈ 17.9 MiB (18.75 МБ децимальных) — при
`Height(720)` это 1.03 GiB RAM против ~18 MiB файла, при `Height(160)` — 52 MiB
RAM против того же файла. Хранить буфер в сжатом виде не получается (см. строку
«replay в сжатом виде» в таблице параметров и «Сжатый кольцевой буфер» ниже),
поэтому единственные способы экономии: буфер уже хранится на **целевом** размере
энкодера, а не на нативном; меньшая высота (`Height(720)`, `Height(160)`);
меньшее число секунд.

### Таблица для нативного экрана 1680×1050

Кольцо хранит raw BGRA на **целевом** размере энкодера, capacity = `seconds × fps`.
Для экрана пользователя 1680×1050 (16:10) один кадр:

- `Full` (нативный 1680×1050) = **7 056 000 Б** (≈ 6.73 MiB);
- `Height(720)` (`label()` → `"720p"`) → 1152×720 (запрошенная высота, ширина
  пропорциональна) = **3 317 760 Б** (≈ 3.16 MiB);
- `Height(1080)` на этом экране = нативный размер (нативная высота 1050 < 1080),
  т.е. считает как `Full` — апскейла нет.

| размер кадра | Б/кадр | fps | секунд | кадров | память |
| --- | --- | --- | --- | --- | --- |
| 1152×720 (`720p`) | 3 317 760 | 30 | 60 | 1 800 | ≈ 5.56 GiB (5 971 968 000 Б) |
| 1680×1050 (`Full`) | 7 056 000 | 30 | 60 | 1 800 | ≈ 11.83 GiB (12 700 800 000 Б) |
| 1152×720 | 3 317 760 | 60 | 60 | 3 600 | ≈ 11.12 GiB |
| 1680×1050 | 7 056 000 | 60 | 60 | 3 600 | ≈ 23.66 GiB |
| 1152×720 | 3 317 760 | 30 | 600 | 18 000 | ≈ 55.6 GiB |
| 1680×1050 | 7 056 000 | 30 | 600 | 18 000 | ≈ 118.3 GiB |
| 1152×720 | 3 317 760 | 60 | 600 | 36 000 | ≈ 111.2 GiB |
| 1680×1050 | 7 056 000 | 60 | 600 | 36 000 | ≈ 236.6 GiB |

Это те же байты, делённые на 1024³ (GiB); в децимальных ГБ первая пара строк даёт
≈ 5.97 и ≈ 12.70 — единицы путать не стоит. Числа — верхняя граница кольца по
формуле, а не измерение: реальное число кадров зависит от того, как часто кадры
действительно приходят (см. «Кольцевой буфер: включение/выключение в рантайме»), и
во время записи кольцо пустое.

## Кольцевой буфер: включение/выключение в рантайме

- `Recorder::enable_replay(seconds)` ставит в канал команд live-сессии
  `EngineCommand::SetReplay(seconds)` и возвращает `Ok(())` сразу — fire-and-forget,
  ack для неё нет. Ёмкость кольца меняется на **следующем захваченном кадре**:
  handler клемпит `seconds` тем же правилом `0..600`, что
  `CaptureConfig::replay_seconds()`, и ставит capacity = `seconds × fps`.
- `Recorder::disable_replay()` — тот же command с `seconds = 0`; при выключении без
  активной записи это ещё и освобождает сессию захвата (см. «Буфер 0 освобождает
  захват»).
- `Recorder::replay_enabled()` читает состояние, **запрошенное фасадом**, без
  roundtrip к capture-потоку: меняется сразу после доставки команды, а не после
  её применения кольцом.
- Выключение сливает кольцо и освобождает память: `ReplayRing::set_capacity(0)`
  присваивает пустой `VecDeque`, поэтому байты кадров и backing-буфер deque'а
  высвобождаются (`clear()` оставил бы аллокацию). Включение поднимает ёмкость и
  **сохраняет уже собранные кадры** — старейшие вытесняются, и оставшиеся кадры
  становятся началом окна нового размера.
- Экономия памяти: во время записи кольцо **не наполняется** — кадры идут на диск,
  и вторая копия им не нужна (кольцо питается только когда энкодера нет), поэтому
  буфер в период записи не удваивает потребление RAM. Включение буфера во время
  записи задаёт пре-ролл для **следующей** записи: наполнение возобновляется
  только после «Стоп» (в демо под кнопкой есть подсказка об этом).
- Честная оговорка про pacing: кадры до старта записи **не расходуют
  pacing-бюджет** — `should_send` вызывается только когда энкодер существует,
  baseline (`last_sent`) стартует с `None`, и первый кадр после создания записи
  отправляется всегда. Значит кольцо наполняется с частотой, с которой кадры
  реально доставляются. Если доставка **чаще** выбранного fps (режим `Default`,
  когда на этой сборке ОС нет `MinUpdateInterval`), кольцо хранит те же `capacity`
  кадров, но покрывает **меньше секунд** истории: память не растёт, история
  короче, чем обещает подпись «N с» в UI.
- Сжатый кольцевой буфер (H.264/HEVC-пакеты в памяти вместо raw BGRA) — **не
  получается сделать средствами библиотеки**: `windows-capture` жёстко фиксирует
  вход энкодера как uncompressed BGRA (`VideoEncodingProperties::CreateUncompressed`,
  `encoder.rs:882-887`), `VideoEncoder` принимает только `send_frame` (GPU-поверхность)
  и `send_frame_buffer` (raw байты), а наружу отдаёт только результат
  `TranscodeAsync()` — stream или файл; `new_from_stream` пишет в in-memory stream
  без truncation и не даёт API для чтения packets. Свой COM-stream поверх прямого dep
  `windows` потребовал бы `unsafe`, которого в крейте быть не может
  (`#![forbid(unsafe_code)`) и нового зависимоста, а это отдельное согласование с
  пользователем. Кольцо остаётся сырым BGRA; экономия RAM — только буфер на
  целевом размере (уже сделано), меньшее разрешение и меньшее число секунд
  (см. «Оценка памяти replay-буфера»).

### Пре-ролл как контракт записи

Пре-ролл — это начало файла, а не отдельный снимок. При «Запись» движок снимает
кольцо (`ReplayRing::take()` в `start_recording`) и передаёт снимок вместе с
энкодером **потоку-писателю** (см. «Писатель энкодера: пре-ролл без фриза»),
который выгружает его через `send_frame_buffer` в порядке старых кадров к новым,
затем пишет live-кадры до «Стоп». При полностью наполненном кольце файл содержит
**минимум N секунд** и включает **N секунд ДО нажатия «Запись»**. Снимок берётся
из кольца один раз на старте записи: после «Стоп» из буфера в файл ничего не дописывается — эти кадры
уже в файле, дублировать их не нужно. Кольцо хранит байты уже в целевом размере
(`raw_bytes_at_target`), поэтому снимок подаётся в энкодер без ресайза; кадры
чужого размера при выгрузке пропускаются.

Честная оговорка к «минимум N»: кадры попадают в кольцо с частотой **фактической
доставки Windows**, не принудительно 30 или 60 fps (см. оговорку про pacing выше).
При редкой доставке — статичный экран, сон, большой `min_update_interval_ms` — в
кольце оказывается меньше `capacity` кадров, и окно пре-ролла получается короче N
секунд; «минимум N» действует только при полностью наполненном кольце.

### Писатель энкодера: пре-ролл без фриза

Выгрузка пре-ролла больше не происходит внутри callback'а захвата. Раньше
`start_recording` подавал кадры кольца прямо в `send_frame_buffer` — при 10 с
буфера это до 300 кадров на одном кадре capture'а — и в записанном ролике
оставался «замороженный» момент нажатия «Запись». Теперь на «Запись» энкодер
создаётся на capture-потоке (WinRT инициализируется только на своём потоке,
поэтому ~1 с создания `VideoEncoder::new` по-прежнему лежит в одном кадре — это
честно оговорено, а не спрятано), а затем вместе со снимком кольца переезжает в
**отдельный поток-писатель** (`EncoderWriter`): он выгружает пре-ролл, дальше
читает живые кадры из ограниченной очереди (`LIVE_QUEUE_FRAMES` = 8 кадров), на
«Стоп» дописывает очередь и делает `finish()`. `VideoEncoder` — `Send`, но не
`Sync`, поэтому владеет им ровно один поток.

Callback захвата при записи делает только копию BGRA-байтов в целевом размере и
неблокирующий `try_send`. Очередь полна — кадр теряется (в логе warn
`encoder writer is lagging; live frame dropped`), захват не фризит. Ограничение
очереди — бюджет RAM: кадр это несколько MiB, так что отстающий писатель стоит
**потерянных кадров**, а не накопленных гигабайт. Порядок подачи — FIFO (кольцо
отдаёт кадры от старых к новым, live-кадры ставятся после `Start`), поэтому
таймстампы в файле монотонны и Media Foundation их принимает.

При записи GPU-путь (`send_frame` поверхностью) **не используется**: `Frame` не
`Send`, поверхность не может уйти из callback'а к писателю, поэтому каждый
записанный кадр идёт байтами — CPU-копия (без padding, с ресайзом при
несовпадении размеров, с переворотом строк), в том числе когда размер совпадает с
целевым.

Acks приходят с разных потоков: «Запись» подтверждается **первым живым кадром**,
попавшим в очередь писателя, «Стоп» — после того как писатель закрыл файл.
`stop()`, закрытие окна (`shutdown`/`Drop`) и уничтожение recorder **не ждут
муксинга**: писатель detached, и файл может дописываться несколько секунд после
«Стоп» — всё это время строка статуса в демо говорит `завершение, запись файла…`.

### Буфер отдельно от записи

Сессию захвата **без записи** создаёт `Recorder::new(config)`: capture-поток
стартует, кольцо наполняется с первого захваченного кадра, файл не пишется —
команда `Start` не ставится. Размер кольца задаёт `config.replay_seconds()` при
создании сессии, на лету его меняют `enable_replay(seconds)` / `disable_replay()`.
В демо это кнопка **«Буфер»**: пре-ролл можно накопить заранее, до любой «Записи»,
и одна живая сессия потом переиспользуется для записей (`Recorder::start(path)`).

### Наполнение кольца: во время записи и после «Стоп»

Кольцо наполняется только когда энкодера нет: во время активной записи оно **не**
наполняется. После «Стоп», как только энкодер закрыт, кольцо наполняется снова при
ёмкости > 0; явно выключенный буфер (`disable_replay()` или ползунок 0) остаётся
выключенным. В демо после «Стоп» при кольце > 0 статус говорит об этом прямо:
«кольцо наполняется заново».

### Буфер 0 освобождает захват

Освобождение сессии — это «захват больше не нужен»: кольцу нечего наполнять
(`ring_capacity == 0`) **и** записи нет. Флаг взводится в двух местах
(spec v3 + v4):

- **После «Стоп»** с выключенным кольцом: `stop_recording` только снимает handle
  писателя — он не ждёт муксинга — done-notice потока-писателя взводит флаг, и на
  следующем захваченном кадре движок отдаёт `EngineEvent::CaptureReleased` и
  вызывает `capture_control.stop()`.
- **Выключение «Буфера» без активной записи** (правка v4): `disable_replay()` —
  команда `SetReplay(0)`; handler клемпит её до ёмкости 0, сливает кольцо и, если
  записи нет, взводит флаг на том же кадре, который прочитал команду — этот же
  кадр закрывает сессию и не обрабатывается (индикатор гаснет на первом
  доставленном кадре после нажатия). Если запись активна, буфер выключается **без**
  освобождения: сессия закрывается после «Стоп» и только когда кольцо уже пустое,
  потому что кадрам записи захват ещё нужен.

В обоих случаях capture-поток завершается, индикатор конфиденциальности Windows
Graphics Capture гаснет, а дальнейшие `start(path)`, `stop()`,
`enable_replay(seconds)`, `disable_replay()` отвечают
`CaptureError::NotConfigured` — нужна новая сессия (`Recorder::new(config)` или
`Recorder::recording(config, path)`), и в демо «Буфер» или «Запись» поднимут её;
`replay_enabled()` продолжает показывать запрошенное состояние. Освобождение без
записи **не является ack'ом ни одной команды**, поэтому фасад читает его отдельным
`Recorder::poll_session_release()`: демо зовёт его на каждой итерации UI рядом с
poll'ами ack, а пока ack висит в очереди опрос ничего не вычитывает (чтобы не
съесть ack). Освобождение в обоих случаях требует доставленного кадра: при редкой
доставке сессия и индикатор могут оставаться открытыми до прихода кадра. Сам
индикатор — штатное поведение ОС, не правится (указание пользователя 2026-11-07).
В демо статус `захват освобождён (буфер выключен)` — с
префиксом `файл записан: <path>, ` после записи — приходит и после «Стоп» с
выключенным буфером, и после выключения «Буфера» без записи.

## Ограничения и риски для ручного Windows-проверения

- **Sparse frame delivery.** На статичном рабочем столе кадров может не быть, и
  тогда `poll_recording_ack`/`poll_stop_ack` выдаёт таймаут 5 с
  (`capture thread did not acknowledge the … request`) вместо зависания — сами
  `start`/`stop` возвращают `Ok(())` сразу и ничего не ждут. Чтобы «Запись»
  подтвердилась, на статичном столе двигайте окно или воспроизведите видео.
- **Выбор энкодера удалён из API (spec v5).** `windows-capture` не предоставляет
  выбора энкодера: Media Foundation сама выбирает HW/SW MFT (hardware acceleration
  включён hard-coded), выбор и наблюдение «что выбрано» недоступны. Опция выбора
  энкодера была удалена из публичного API целиком — это **удалено из API, а не
  «не получилось сделать»**: `CaptureConfig` просто не имеет поля энкодера, и демо
  больше не показывает контрол выбора.
- **Режимы битрейта (CQP/CRF) удалены из API (spec v5).** Реально существует
  только CBR: `bitrate(u32)` ложится в `MF_MT_AVG_BITRATE`; quality-режимы
  требовали бы `ICodecAPI`, которого библиотека не использует, — они никогда не
  передавались. Опция режима битрейта удалена из API целиком (это **удалено из
  API, а не «не получается»**); в API остаётся только `bitrate_kbps`.
- **Нулевой fps и нулевая высота отвергаются до захвата.**
  `CaptureConfig::invalid_reason()` называет их по-русски («частота кадров 0
  недопустима: нужен fps от 1», «высота разрешения 0 недопустима: нужна высота от
  1 пикселя»), и каждый конструктор `Recorder` (`new`, `recording`,
  `with_debug_dump`) отвечает `CaptureError::NotConfigured` — типизированная
  ошибка, не panic. Контролы демо ограничивают fps от 1 и высоту от 1, так что UI
  нулевых значений не запрашивает.
- **Целевой размер фиксируется при создании `Recorder`.** Нативный размер монитора
  читается при создании recorder (на Windows, `Monitor::primary()`) и `target_size`
  считается один раз; смена высоты/fps/фильтра в UI действует только со следующим
  «Запись» или «Буфер», когда демо строит новый `Recorder` (живой сессии нет или
  включены debug-дампы), — поверх живой сессии `start(path)` параметры текущего
  потока не меняет.
- **`image`-фильтры не влезают в реальное время.** `CatmullRom`/`Gaussian`/`Lanczos3`
  стоят 148…207 мс/кадр на 1680×1050 → 1152×720, т.е. capture-поток физически не
  успевает ни на 30, ни на 60 fps: запись получается рывками (кадр раз в несколько
  секунд). Для плавности дефолт — свой `Bilinear` (~10 мс/кадр); на `Full`/нативном
  размере ресайза нет вовсе, и плавность зависит только от delivery/pacing.
- **Пути требуют существующей родительской папки.** `validate_output_path` отвергает
  пустой путь и путь, у которого родитель не является существующей директорией
  (`CaptureError::InvalidPath`); demo создаёт папку заранее.
- **Ошибки MF могут всплывать на `finish()`.** Файл создаётся при старте, но flush +
  mux делает **поток-писатель** после «Стоп» (или после закрытия захвата в
  `on_closed`), поэтому ошибка энкодера приходит как `CaptureError::Encoder` в
  `poll_stop_ack()` — уже после нажатия «Стоп», и пока писатель дописывает файл,
  статус говорит `завершение, запись файла…`.
- **Создание энкодера — ~1 с на capture-потоке.** WinRT инициализируется только на
  своём потоке, поэтому `VideoEncoder::new` не переезжает к писателю (перенос
  потребовал бы `unsafe`, которого в крейте быть не может): один кадр при «Запись»
  бывает длинным — это цена создания энкодера, и она оговорена, а не спрятана.
  «Замороженного» момента в записанном файле от этого не остаётся: пре-ролл
  выгружает писатель.
- **Аудио — заглушка, трек всегда disabled.** Даже если в config стоит
  `System`/`Mic`/`Both`, крейт вызывает `disabled(true)`: звук не пишется, файл —
  video-only. `AudioMode` остаётся в API как маркер (`is_supported()` — только
  `none`): аудио **не реализовано**, решение по аудио за пользователем.
- **fps не гарантирован.** `MinimumUpdateIntervalSettings::Custom` — hint; на хостах без WinRT-свойства `MinUpdateInterval` (older Windows builds) крейт автоматически откатывается на `Default` (в логах — `interval=default` + warn), fps ограничивается pacing'ом по timestamp. Команда `Start` исполняется на capture-потоке и подтверждается первым живым кадром, `Stop` — с потока-писателя после закрытия файла; вызывающего ни одна не блокирует. Graphics Capture отдаёт кадры только при изменениях содержимого экрана: статичный стол = sparse delivery, replay-буфер почти не наполняется, а ack может выдать таймаут 5 с. Для реальной записи и replay на статичном столе двигайте окно или воспроизведите видео.
- **Resize — CPU.** При несовпадении размеров каждый кадр проходит BGRA-ресайт
  фильтром из `scale_filter` (по умолчанию свой `Bilinear`, ~10 мс/кадр; `image`
  дороже — см. «Масштабирование и фильтры») — это CPU-стоимость на кадр; при
  совпадении размеров (в т.ч. `Full` и высота выше нативной) ресайза нет, но при
  записи кадр всё равно копируется байтами и переворачивается, потому что GPU-путь
  `send_frame` при записи не используется (`Frame` не `Send`).
- **Ориентация кадров на raw-buffer пути.** CPU-буфер захвата — сверху вниз, а
  Media Foundation на пути `send_frame_buffer` рендерит такие байты вверх ногами
  (проверено debug-дампом на Windows 1680×1050 → 1280×720). Engine разворачивает
  строки (`flip_rows_bgra`) перед подачей и складывает в replay-буфер уже
  развёрнутые байты; при записи переворот применяется и на нативном размере,
  потому что все записанные кадры идут raw-buffer путём.
- **Живой энкодер может умереть.** Ошибка `send_frame_buffer` (на пре-ролле или на
  live-кадре) или `finish()` не убивает захват: писатель прекращает запись, приходит
  `EngineEvent::CommandFailed` с потока-писателя, replay-буфер продолжает
  наполняться. При ошибке подачи энкодер сбрасывается **без** `finish()` — второй
  ошибки на мёртвом энкодер не бывает, поэтому файл остаётся недомуксинным. Если
  поток-писатель умер, не оставив done-notice, capture замечает это по
  `is_finished` и тоже сообщает `CommandFailed`.
- **Писатель может отстать.** Очередь живых кадров ограничена 8 кадрами
  (`LIVE_QUEUE_FRAMES`): при отставании энкодера новый кадр не ставится и теряется
  (warn в логе), запись получается с пропусками — зато capture и UI не фризятся, а
  RAM не растёт.
- **HEVC зависит от машины.** Доступность HEVC MFT определяет Media Foundation на
  конкретном Windows-хосте; при отсутствии энкодера ошибка приходит при создании
  энкодера (на «Запись»).
- **Индикатор захвата Windows (жёлтая рамка) — штатное поведение ОС, не баг.**
  Capture-сессия открыта с момента создания `Recorder` (capture-поток запускается в
  конструкторе) и закрывается только при `shutdown()`/уничтожении recorder — в демо
  это закрытие окна. После «Стоп» индикатор остаётся, если кольцо включено (ёмкость
  > 0): запись закончена, но захват продолжает работать ради кольца. Исключения
  (spec v3 + v4): при кольце 0 «Стоп» освобождает сессию, и выключение «Буфера»
  без активной записи освобождает её на ближайшем доставленном кадре —
  capture-поток останавливается и индикатор гаснет (см. «Буфер 0 освобождает
  захват»). Сам индикатор не правится: это штатное поведение ОС, пользователь
  подтвердил 2026-11-07.
- **`Recorder` не `Clone`.** Один capture-поток и один канал команд, методы берут
  `&mut self`. `Drop` делает `shutdown()` — брошенный recorder не оставляет
  capture-поток; detached поток-писатель, если запись была жива, дописывает файл
  сам и не ждёт его.

## Краткий API-пример

```rust
use std::path::Path;

use video_capture::Recorder;
use video_capture::config::{AudioMode, CaptureConfig, Codec, Resolution, ScaleFilter};

let config = CaptureConfig {
    codec: Codec::H264,
    bitrate_kbps: 15_000,
    // Произвольная высота (u16): Height(720) — label "720p", Height(160) —
    // "160p"; Resolution::Full — нативный размер монитора. По умолчанию — P1080.
    resolution: Resolution::Height(720),
    scale_filter: ScaleFilter::Bilinear,
    // fps — u8 от 1; 0 отвергается конструкторами (CaptureError::NotConfigured).
    fps: 30,
    replay_seconds: 30,
    audio: AudioMode::None,
};

// Сессия захвата **без записи** — только кольцо пре-ролла: capture-поток стартует,
// кольцо наполняется с первого захваченного кадра, файл не пишется (Start не
// ставится). Размер кольца задаёт `replay_seconds` в конфиге.
let mut buffer = Recorder::new(config)?;

// Пре-ролл в рантайме: fire-and-forget, применяется на ближайшем захваченном
// кадре; `replay_enabled()` читает состояние, запрошенное фасадом (без roundtrip).
// Включение поднимает ёмкость и сохраняет кадры, уже собранные в кольце.
buffer.enable_replay(60)?;

// «Запись» поверх живой сессии: команда Start ложится в очередь и возвращает
// `Ok(())` сразу. Энкодер создаётся на capture-потоке (~1 с в одном кадре — WinRT
// живёт только на своём потоке) и переезжает в поток-писатель вместе со снимком
// кольца (`ReplayRing::take()`); писатель выгружает пре-ролл через
// `send_frame_buffer`, дальше читает live-кадры из очереди в 8 кадров. Файл
// начинается с кадров ДО нажатия, дальше live-запись. Ack — первый живой кадр,
// попавший к писателю.
buffer.start("C:\\Users\\me\\Videos\\clip.mp4")?;
while buffer.poll_recording_ack().is_none() {
    // ... живая итерация UI (в демо это просто опрос на каждом update-пассе)
}

// Завершение — очередная команда: `Ok(())` сразу; flush + mux делает detached
// поток-писатель, который по «Стоп» закрывает очередь живых кадров и дописывает
// файл — несколько секунд после нажатия. При ёмкости кольца > 0 захват
// продолжает работать ради кольца и оно наполняется заново; при ёмкости 0 этот
// «Стоп» освобождает сессию (см. ниже).
buffer.stop()?;
while buffer.poll_stop_ack().is_none() {
    // ... файл ещё дописывается
}

// Выключение буфера без активной записи (`disable_replay()` = `SetReplay(0)`)
// сливает кольцо **и** освобождает сессию на ближайшем доставленном кадре.
// Освобождение без очереди команд — не ack ни одной команды, поэтому его читает
// отдельный опрос на той же итерации UI.
buffer.disable_replay()?;
if buffer.poll_session_release() {
    // ... индикатор захвата гаснет; `start`, `stop`, `enable_replay` и
    // `disable_replay` теперь отвечают `CaptureError::NotConfigured`
}
// Новая сессия под кольцо — тот же конструктор (в демо это делает кнопка «Буфер»).
let mut buffer = Recorder::new(config)?;

// Сессия захвата с записью «на первом же кадре»: команда Start поставлена в
// очередь ДО запуска capture-потока. Путь проверяется до создания потока, поэтому
// InvalidPath не оставляет живого потока. Возврат — `Ok(())` сразу, без ожидания
// ack. Ошибки старта: нет primary monitor, WinRT/Direct3D init, старт потока.
// `scale_filter` работает только когда размер кадра ≠ целевой: на `Full` и на
// высоте выше нативной целевой остаётся нативный размер — ресайза нет, но при
// записи кадр всё равно подаётся байтами — GPU-путь `send_frame` при записи не
// используется (`Frame` не `Send`).
let mut recorder = Recorder::recording(config, Path::new("C:\\Users\\me\\Videos\\clip.mp4"))?;

// Ожидание читается в цикле вызывающего (в демо — на каждой итерации UI):
// `None` — ещё ожидание; `Some(Ok(()))` — запись активна; `Some(Err(..))` —
// ошибка команды или таймаут 5 с без ack.
while recorder.poll_recording_ack().is_none() {
    // ... живая итерация UI
}

recorder.stop()?;
while recorder.poll_stop_ack().is_none() {
    // ... файл ещё дописывается
}

// Освобождение сессии — только когда кольцо выключено (ёмкость 0) **и** записи
// нет: либо после «Стоп» (done-notice писателя взводит флаг на следующем кадре),
// либо на кадре, прочитавшем `disable_replay()` без активной записи. Движок
// отдаёт `EngineEvent::CaptureReleased` и вызывает `capture_control.stop()`;
// capture-поток завершается, индикатор захвата Windows гаснет, тот кадр не
// обрабатывается. Фасад помечает сессию освобождённой, и `start`, `stop`,
// `enable_replay`, `disable_replay` отвечают `CaptureError::NotConfigured`;
// дальше нужен новый `Recorder::new(config)` или `Recorder::recording(config, path)`.
// Прочитать освобождение можно только `Recorder::poll_session_release()` (см.
// выше): ни один ack его не приносит.

// Останавливает capture-поток, join'ит его и возвращает ошибку, которую поток
// сообщил по дороге (например `CommandFailed` от потока-писателя). Detached
// писатель не ждёт: незакрытый файл тот дописывает сам и завершается.
recorder.shutdown()?;
```

На Linux `Recorder::new` возвращает `Ok` (поток не запускается), а конструкторы
`recording` и `with_debug_dump` — `CaptureError::UnsupportedPlatform`; все три
конструктора сначала отвергают недопустимый config `CaptureError::NotConfigured` —
валидность конфига не зависит от платформы. Capture-методы `start`, `stop`,
`enable_replay`, `disable_replay` и `shutdown` возвращают
`CaptureError::UnsupportedPlatform`; оба poll'а ack дают `None` (очередь пуста),
`poll_session_release()` — `false`, а `replay_enabled()` показывает состояние,
запрошенное фасадом.
