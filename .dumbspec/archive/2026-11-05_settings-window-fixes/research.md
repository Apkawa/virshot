## Template placeholders help

Source: read-only survey (subagent run), verified in `src/template.rs` / `src/config.rs` / `src/capture.rs`.

- **Authoritative token set = 11 exact spellings: `%Y %y %mo %d %H %M %S %iso %t %n %ext`** (`src/template.rs:16`, private `const TOKENS`). Nothing else is recognized — no `%app`, `%m`, `%month`, `%f`.
- `render(template, now, title, ext, counter)` `template.rs:64-86`; `token_value :150-176`: `%Y` 4-digit year, `%y` 2-digit, `%mo` zero-padded month, `%d` day, `%H/%M/%S` zero-padded time, `%iso` = `YYYY-MM-DD_HH-mm-ss` (local), `%t` = sanitized + truncated-to-60 window title (`TITLE_MAX_CHARS :19`, empty → `untitled`, `FULLSCREEN_LITERAL :25` = `fullscreen` when no title), `%n` = collision counter (normally 1), `%ext` = extension from `Format::extension()` (`config.rs:375-384` → `png|jpg|webp`).
- **Case-sensitive**; any unrecognized `%…` (incl. lone `%`) → typed `Error::UnknownToken` (`template.rs:45`, message quotes the template), surfaced at **capture time** (toast + log), never at Apply — `apply()` does no validation. No escape syntax for a literal `%`.
- Path rules: relative to `save_path` only; absolute (`/`, `\`, UNC, `C:`) and `..` segments rejected (`is_absolute :107-111`, `ParentSegment`); `/` and `\` both act as separators, output normalized to `/`; every segment sanitized (`<>:"/\|?*` + control chars → `-`, empty → `untitled`); missing subfolders created at save (`capture.rs:492-495`).
- `%t`/`%n` are context-dependent: `%t` = window title in Window mode, literal `fullscreen` in Full-screen mode (`capture.rs:328-330`); `%n` re-rendered with counter 2..1000 only when the template literally contains `%n` (`capture.rs:458`), otherwise `-N` suffix before the extension (`collision_variant :93-104`, cap `COLLISION_MAX_COUNTERS = 1000`).
- **UI today:** `general_tab` `src/gui.rs:816-861` — "Save path" + Browse `:820-825`, "Full-screen template" `:832-833`, "Window template" `:835-836` (plain `text_edit_singleline`), Format combo `:838-844`, quality DragValues `:846-860`. **No token hint/help text anywhere**; no collapsible widget in `gui.rs`; `gui.rs` does not import `crate::template`. Inline parenthetical hint precedent exists at `:859`.
- **No display-list helper:** `TOKENS` is module-private, `template.rs` exports only `render`/`collision_variant`/`Error` → a UI list must be hardcoded, nothing keeps it in sync today (no test compares a UI list to `TOKENS`).
- **Docs:** `docs/spec.md:45` + §4.2 `:172-184` list the same 11 tokens; `README.md:100-105`. Spec §4.4 `:275-277`/§7 `:369-372` quote **different** default templates (extra `%y-%mo-%d` segment, save `%USERPROFILE%\Pictures\Screenshots`) than shipped code defaults (`config.rs:424-425`: `FullScreen/%y-%mo/%iso.%ext`, `%t/%y-%mo/%t-%iso.%ext`; save `<home>/Pictures/ViRShot` `:319-330`) → accordion must quote **code** values if it quotes defaults.
- UI language must be English (spec §4.4 `:267`).
- Tests pin expansion: `src/template.tests.rs` (`render_all_tokens_in_one_segment_expands_in_order :59`, `render_unknown_token_is_rejected_with_token_name :218`, `render_strftime_minute_token_is_rejected :228`, `render_lone_percent_is_rejected :237`, sanitization `:111-166`); `src/config.tests.rs:4-17` pins shipped defaults verbatim; `src/capture.tests.rs:218/:255/:315`.

## Duplicate bindings (facts gathered from the surveys above)

- No validation exists in the save path (`config::save` `src/config.rs:167-171` writes whatever `Settings` holds); duplicate detection has **no home today** and must live in the GUI before save (task scope excludes config-format changes).
- OS-level behavior: `HotKey::id = (mods.bits() << 16) | Code as u32` (`global-hotkey/src/hotkey.rs:52-59`), Windows `RegisterHotKey` returns `ERROR_HOTKEY_ALREADY_REGISTERED` → `Error::AlreadyRegistered` (`windows/mod.rs:104-105`) → `Registration::Failed { reason }` shown as the row warning tooltip (`src/hotkeys.rs:370-374`, `src/gui.rs:448-460`). So a duplicate combo already surfaces as a registration failure, but only **after** Apply — nothing blocks saving it.
- Pad duplicates: runtime matching is index-bit based (`src/gamepad.rs:534-540`) and actions fire through one shared debounce gate (`bindings::try_fire_shared :151`), so the same pad string on several actions is functionally ambiguous.
- `parse_controls` (`src/bindings.rs:164-170`) aborts on the first error (first failure wins) — a rejected draft must never reach `config::save`.


## PrintScreen binding does not fire (v2 investigation)

Read-only investigation, 2026-11-06. No source file was touched; scratch drivers/logs live in `.tmp/` (`ps-driver.sh`, `grabprobe.rs`, `frame-origin.py`, runs under `.tmp/ui-verify/ps-*`).

### Layer 1 — bind-by-press capture: PrintScreen DOES arrive and commit (verified)
- `SUPPORTED_KEY_NAMES` lists `"PrintScreen"` first (`src/gui.rs:325`); `supported_key_name` (`src/gui.rs:535-548`) maps `egui::Key::PrintScreen` → `"PrintScreen"` via `Key::name()` (`egui-0.37.0/src/data/key.rs:296` declaration, `:482` in `Key::ALL`, `:854` `name()`, `:655` `from_name`). Pinned by `src/gui.tests.rs:38-98`.
- Capture loop `handle_capture_press` (`src/gui.rs:1250-1302`) matches `egui::Event::Key { key, pressed: true, repeat: false, .. }` and commits with `binding_from_press` (`:579`) — nothing PrintScreen-specific blocks it.
- Upstream pipeline delivers it on both platforms, and never swallows it:
  - `egui-winit-0.37.0/src/lib.rs:1659` `NamedKey::PrintScreen => Key::PrintScreen`; `:1813` `KeyCode::PrintScreen => Key::PrintScreen` (physical fallback); `Event::Key` push `:1155-1161` with `active_key = logical_key.or(physical_key)`; `Event::Text` only for printable text `:1164-1171` ⇒ PrintScreen never produces `Event::Text`; the clipboard early-return `:1129-1152` (Cut/Copy/Paste) does not match bare PrintScreen (predicates `:1538-1554`).
  - winit X11: `keysyms::Print => NamedKey::PrintScreen` (`winit-0.30.13/src/platform_impl/linux/common/xkb/keymap.rs:501`; also `Sys_Req :454`, `KeyCode::PrintScreen :141`).
  - winit Windows: `VK_SNAPSHOT => Key::Named(NamedKey::PrintScreen)` (`windows/keyboard_layout.rs:802`), `KeyCode::PrintScreen => VK_SNAPSHOT` (`:648`); PrintScreen arrives as plain `WM_KEYDOWN` (`windows/event_loop.rs:1127`, `:1767` — only `WM_SYSKEYDOWN` is deferred to `DefWindowProc`), so `Event::Key{physical: PrintScreen}` reaches egui even when `ToUnicode` yields no logical char.
- **Observed** (`Xvfb` + openbox with an empty `<keybindings/>`, run `.tmp/ui-verify/ps-capture-print`): Hotkeys tab → bind button → `xdotool key Print` ⇒ row label became `PrintScreen` (`shots/crop-04-print-bound.png`), config written `key = "PrintScreen", mods = []` (`config.toml:10-11`), log `Hotkeys paused for rebind (2 combo(s) unregistered)` → `Hotkeys restored (…)` (`virshot.log:14-15`). Controls: `Caps_Lock` during capture is ignored (row stays "Press keys…", `ps-capture-caps-ctrl/shots/crop-04-after-caps.png`), `Insert` binds normally (`ps-capture-insert-ctrl`).
- Conclusion: layer 1 is not the cause. PrintScreen is captured, savable, and registered/saved exactly like `Delete`/`Insert`.

### Layer 2 — registration: the Linux failure is an external grab, not our code
- `.tmp/grabprobe` (x11rb, mirrors `global-hotkey-0.9.0/src/platform_impl/x11/mod.rs:101-160` — `grab_key(false, root, mods|ignored, keycode, ASYNC, ASYNC)` over ignored masks `[0, M2, LOCK, M2|LOCK]`, `ErrorKind::Access` ⇒ ungrab + `Error::AlreadyRegistered`):
  - **No WM** (`.tmp/grabprobe-nowm.log`): bare/alt/ctrl PrintScreen `OK`; Delete/Insert/PageUp `OK`. Second client requesting the same bare keycode ⇒ `Access` (`GrabKey`, error_kind Access), masked variants still `OK`.
  - **openbox default config** (`.tmp/grabprobe-openbox.log`): bare `Access`, alt `Access`, numlock `Access`, capslock `Access`, **ctrl `OK`**; Delete/Insert/PageUp all `OK`.
  - **openbox with `<keybindings/>` empty** (`.tmp/ui-verify/ps-grab-empty-rc.log`): everything `OK` — identical to the no-WM case.
- X11 rule confirmed experimentally: `GrabKey(keycode, mask m)` fails with `BadAccess` if another client holds that keycode with a mask `m'` such that `m ⊆ m'`. Mask 0 (bare) is a subset of every mask ⇒ any existing grab on the keycode blocks a bare grab; a *different* modifier family (Ctrl) still succeeds.
- The blocking client in the harness is openbox's stock config: `/etc/xdg/openbox/rc.xml:316` binds **bare `Print` → `scrot`** and `:249` binds **`A-Print` → `scrot -s`** (`:240` `A-Escape` → Lower). Bare `Print` is genuinely taken by the WM, so both VIRShot registrations fail and the keypress never reaches the app.
- Xvfb artifact worth noting: Xvfb's minimal keymap puts `Print (0xFF61)` and `Escape (0xFF61…0xFF1B)` on **keycode 107** (`keysyms at this keycode: [65377, 65301, 65377, 65301]`), which is why `A-Escape` also blocks Print here. `keysym_to_keycode` (`x11/mod.rs:510-528`) picks the first matching keycode, so on a keymap where Print shares a keycode with another keysym a bare PrintScreen registration also grabs that other key. Real desktop keymaps give Print its own keycode.
- **Observed app behavior** — verbatim reproduction of the reported symptom (`/etc/xdg` fallback): `.tmp/ui-verify/ps-wm-default-rc/virshot.log:3-4` = `ERROR … Hotkey not registered: PrintScreen (full_screen): HotKey already registered: HotKey { mods: Modifiers(0x0), key: PrintScreen, id: 117 }` and the same for `alt+PrintScreen (window) id: 65653`. With the empty-keybinding WM: `ps-wm-empty-rc/virshot.log:3-4` = `Hotkey registered: PrintScreen (full_screen)` / `Hotkey registered: alt+PrintScreen (window)`. Under the default WM the row also stays in "Press keys…" forever when capturing Print (`ps-capture-default-rc`: `paused` at `virshot.log:14`, no restore) — the WM grab eats the KeyPress, exactly the hazard spec §4.4 documents (`docs/spec.md:286`).
- Conclusion: layer 2 on Linux is environmental (WM/user app grabs). Our code reports it correctly: `Registration::Failed { reason }` (`src/hotkeys.rs:355-374`) → per-row warning tooltip (`src/gui.rs:448-460`) + `ERROR` log (`src/main.rs:465-483`). `Ctrl+PrintScreen` (rect) is reserved and never registered (`src/hotkeys.rs:357-360`).

### Layer 3 — firing: works as soon as registration succeeds
- **Observed** (`ps-wm-empty-rc`): `xdotool key Print` ⇒ `INFO virshot::capture: Saved: …/out/FullScreen/26-11/2026-11-06_10-48-58.png` (`virshot.log:14`), file exists.
- **Observed** (`ps-fire-alt`): bare Print → `Saved: …FullScreen…`; `alt+Print` reached the Window action (`ERROR … Capture failed: no active window` — an xcap/Xvfb artifact with no WM-tracked active window, but it proves the hotkey event arrived and ran through `bindings::try_fire_shared`, `src/bindings.rs:168-179`).
- Conclusion: layer 3 is fine; the trigger path is key-agnostic (`GlobalHotKeyEvent` drain → id→action map in `src/hotkeys.rs`).

### Windows path (analysis only — Windows runtime cannot be executed in this sandbox)
- Code shape is PrintScreen-friendly: `Code::PrintScreen => VK_SNAPSHOT` (`global-hotkey-0.9.0/src/platform_impl/windows/mod.rs:278`), `RegisterHotKey(self.hwnd, hotkey.id(), mods, vk_code)` with `MOD_NOREPEAT` always added (`:76-115`), `ERROR_HOTKEY_ALREADY_REGISTERED ⇒ Error::AlreadyRegistered` (`:104-105`), `WM_HOTKEY → GlobalHotKeyEvent{id, Pressed}` + async-state Release thread (`:151-168`). Manager is created on the main thread so winit's pump dispatches `WM_HOTKEY` to global-hotkey's hidden window (`src/hotkeys.rs:1-55`).
- Microsoft's own note is the load-bearing fact: RegisterHotKey "fails if the keystrokes specified for the hot key have already been registered for another hot key. However, some pre-existing, default hotkeys registered by the OS (**such as PrintScreen, which launches the Snipping tool**) may be **overridden by another hot key registration when one of the app's windows is in the foreground**" ([MS Learn: RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey)).
- Ordering gap (inferred consequence): initial registration runs at `src/main.rs:361`, **before** `gui::run` (`:404`) creates any window ⇒ at startup no VIRShot window is in the foreground, so on Win11 with the Snipping Tool holding PrintScreen the bare-PrintScreen registration plausibly fails with "HotKey already registered" while `Delete`/`Insert` register fine. Re-registration does happen while our window is foreground: Apply/OK (`src/gui.rs:1094-1120` → `controller.apply`, `src/hotkeys.rs:253-277`) and capture restore (`src/gui.rs:1226-1234`).
- Fix options for Windows, cost/risk:
  1. **Defer initial registration until the settings window exists and is focused** (move the `HotkeysController::start` registration out of `main.rs:361` into the GUI create/first-frame path). Low cost, exploits the documented foreground override; risk: behavior depends on OS willingness to override, and registration status must still be surfaced for rows that fail.
  2. **Retry failed registrations on window activation/focus** (small retry state in `hotkeys.rs`, driven by `gui::run` focus events). Medium cost; risk: repeated noisy attempts/log spam; must not re-register while capture is paused.
  3. **Docs + UX only**: keep the OS limit, sharpen the tooltip/log wording (currently the crate's raw `Debug` string `HotKey already registered: HotKey { … }`) and point at disabling the Win11 "Use PrintScreen for Snipping Tool" setting (`README.md:28`, `docs/spec.md:426`). Lowest risk, no behavior change.
  - Rejected: a low-level keyboard hook (`WH_KEYBOARD_LL`) or raw-input fallback would need `unsafe` (forbidden, `#![forbid(unsafe_code)]`) and/or a new dependency (needs user approval), and bare PrintScreen without a hotkey cannot fire while the game is foreground (spec §2, `docs/spec.md:102`).
- Note: `HotKey::id = (mods.bits() << 16) | Code` (`global-hotkey/src/hotkey.rs:52-59`) produces ids above the documented app range `0x0000..0xBFFF` (e.g. 65653 for Alt+PrintScreen). Registered with a non-NULL HWND; global-hotkey does this on every combo and is widely used, so it is a curiosity, not a suspected cause.

## Windows runtime evidence (v3): the press never reaches egui

Evidence from the user's Windows host (`log-level=debug`, `.tmp/printscreen-report.md` carries the external investigation):

- Startup registration SUCCEEDS on Windows: `Hotkey registered: PrintScreen (full_screen)`,
  `Hotkey registered: alt+PrintScreen (window)`, rect combo logged as reserved. So the OS
  default hotkey is not held and Stage 13's retry is irrelevant for this symptom.
- During a bind capture the row stays "Press keys…" until Escape: the log shows only
  `Hotkeys paused for rebind (2 combo(s) unregistered)` → `Hotkeys restored (...)` pairs,
  with no commit — i.e. no `egui::Event::Key { key: PrintScreen }` was ever delivered.
- Root cause (vendored `winit 0.30.13`, `src/platform_impl/windows/keyboard.rs:106-155`):
  on `WM_KEYDOWN | WM_SYSKEYDOWN` the builder peeks `next_kbd_msg(hwnd)`; if the next queued
  message is NOT another keyboard message it treats it as belonging to this key, stores
  `PartialKeyEventInfo` in `event_info` and returns `MatchResult::TokenToRemove` — the event
  is dispatched only later by `WM_CHAR`/`WM_DEADCHAR` (`:156-167`). Windows sends no char
  message for `VK_SNAPSHOT`, so the stored event is discarded by the next keydown
  (`*event_info = None`, `:124-125`) and the press is lost. Keys that do produce a char
  message (letters, digits) or that happen to be followed by another keyboard message
  (`Delete`, F-keys) still arrive, which matches the observed "Delete works".
- External corroboration: no upstream winit issue/fix for this after 0.30.13; other projects
  hit the same OS behavior (imgui changelog: "Windows doesn't emit it") and synthesize the
  press from a different source.

Decision (user-approved approach): synthesize the press from our own safe hotkey layer instead
of touching winit. While a keyboard capture is active (`hotkeys::pause` already unregistered
the live combos), register probe combos for keys Windows never delivers — `PrintScreen`,
`ScrollLock`, `Pause`, list extensible — bare + Alt/Ctrl/Shift (+ Alt+Shift, Ctrl+Shift;
Win is unreachable in capture). The listener recognizes a probe id, records
`ProbePress { code, mods }` into a shared slot and wakes eframe via `request_repaint`
(same shape as `ToastHandoff`); the GUI drains it in `logic` and commits it as a normal
press. Windows-only (`cfg(windows)`): on Linux/X11 the keysym arrives normally, so probes
would be pure noise. Tradeoff, documented in `docs/spec.md`: while capturing, a probe combo
temporarily blocks the OS default (Snipping Tool) for that key — acceptable, capture-scoped,
and it is exactly what the action binding already does when registered.
