# 2026-11-15_settings-first-start-only: окно настроек только при первом запуске

**Created:** 2026-11-15T17:47:58+03:00

## Scope

- Окно настроек показывается при старте резидентного приложения **только при первом запуске** — когда файла конфига нет; при этом конфиг создаётся с дефолтными настройками (текущее поведение `load_or_create`, сохраняется).
- При всех последующих запусках (файл конфига уже существует) окно настроек **не показывается**: приложение стартует скрытым в трей. Открытие окна — из трея (левый клик / меню «Настройки») как сейчас (`ViewportCommand::Visible(true)`).
- (v3) Окно настроек вообще **не существует до открытия из трея** — UI живёт в дочерном viewport, который создаётся только при показе; на экране ничего не мелькает. Коревое окно не несёт UI и остаётся скрытым.
- «Первый запуск» = файл конфига не существовал до старта и был создан дефолтом. Повреждённый/нечитаемый конфиг дефолтом **не перезаписывается** (текущее поведение, spec §7) и **не** считается первым запуском — окно не показывается, приложение работает на дефолтах с ERROR-логом.
- Автозапуск (HKCU Run) после этого старта тоже работает скрыто — ожидаемое следствие.
- Out of scope: содержимое/структура конфига, семантика Apply/OK/Cancel, закрытие в трей, headless-режим `shot`, новый CLI-флаг, авто-показ окна при повреждённом конфиге.

## Approach

- Сигнал «файл был создан» рождается внутри `config::load_or_create` (единственное место, где проверяется `!path.exists()`, config.rs:167). Функция меняет сигнатуру на `(Settings, bool)` — второй флаг «дефолтный файл создан» (или равнозначный `pub(crate)` результат того же модуля).
- `run_resident` (main.rs:428–544) передаёт этот флаг в `gui::run(...)` параметром `visible`. `gui::run` (gui/window.rs:140) добавляет `with_visible(visible)` на корневом `ViewportBuilder`.
- `gui::run` **не пропускается** при обычном запуске: в create-closure живут `OverlayHost`, `ToastService` и `capture::attach_handoff`, а loop обслуживает tray-опрос (500 ms), хоткеи и геймпад-помп; скрытый viewport сохраняет всю эту обвязку и повторное открытие окна из трея. Пропуск `gui::run` равен `park_without_gui` (только WARN, без открытия окна) — не наша цель.
- `run_shot` (main.rs:329) игнорирует флаг (headless-режим не меняется; e2e `cli_headless` продолжает проверять авто-создание конфига).
- unit tests (TDD): `load_or_create` возвращает `created=true` для отсутствующего файла и `false` для существующего/повреждённого (существующие тесты в config.tests.rs обновляются под новую сигнатуру). Решение «показывать ли окно» = `created`, отдельной второй функции не заводим (KISS).
- docs/spec.md: добавить формулировку в §4.5 (окно открывается при первом запуске; последующие запуски — скрытый старт, открытие из трея). §2:125 «скрытый запуск» и §7 авто-создание дефолта — уже описаны, новых противоречий нет.
- **v2 — подавление eframe reveal (добавлено по отчёту пользователя: окно открывалось несмотря на `with_visible(false)`).** eframe 0.37 glow на Windows безусловно показывает коревой viewport после первого кадра (`post_rendering` → `set_visible(true)`, PR #2279), и первый кадр красится синхронно на `Resumed` — `with_visible(false)` переиграть не может. Промежуточное решение через `startup_hidden` + `ViewportCommand::Visible(false)` каждый logic-pass (исполнено в Stage 4).
- **v3 — окно настроек из трея, без флеша (по отчёту пользователя: «костыльно, окно на мгновение показывается и исчезает»; трей приоритетнее экрана настроек).** Коревое окно больше не несёт UI настроек и всегда скрыто (подавление Stage 4 остаётся — пустое коревое окно, флеш невидим содержимым). Окно настроек — дочерный viewport `virshot-settings`, создаётся только когда его реально нужно показать, по существующим паттернам репо: state-machine с флагами как `AboutWindow` + spawn-рецептор чипов (`show_viewport_deferred` с `.with_visible(false)`, `RequestPaintWhileHidden` на ROOT для full-pass — logic-only pass окна не создаёт, `Visible(true)` дочернему viewport после первого paint, throttle как `schedule_child_viewport_repaint`). Реveal-флаг eframe глобальный на приложение и consumptionится root'ом на стартовом paint, поэтому child не получает auto-reveal — `Visible(true)` показывает окно без флеша.
  - Первый запуск: окно открывают сразу после старта (spawn hidden → painted → `Visible(true)`); последующие: дочерный viewport существует скрытым, `ShowSettings` из трея — `Visible(true)` (уже открыто — `Focus`, как About).
  - Закрытие X окна настроек = скрытие в трей (child record close → `Visible(false)`, draft откатывается к applied, как нынешний HideToTray); выход — только `Exit` из трея / OK/Cancel (root Close), как сейчас.
  - Машинерия остаётся в root `logic`: tray poll, update-дрены, install, chip drive, pad/probe drains, suppression root. Root `ui` становится пустым (полные passes всё равно вызываются).
  - Дочерний pane — непрозрачный CentralPanel (children наследуют `transparent` root'а, паттерн about.rs:240). Builder константен per viewport id (chrome-флаги реконструируют окно).
  - Persisted window geometry (eframe autosave пишет painting-window в один key) — известная nuance, вне scope: root скрыт, restore безвреден.
- **v4 — невидимый root вместо подавления (отчёт пользователя: флеш остался; при удалённом конфиге сначала на мгновение появляется пустое окно, потом экран настроек).** Коревое окно на Windows безусловно показывается на первом кадре (`is_first_frame → set_visible(true)`), и suppression `Visible(false)` приходит только на следующем pass — видимый флеш пустого кадра с рамкой/заголовком. Правка: коревое окно делается визуально инертным — `decorations(false)`, крошечный `inner_size` (1×1), `transparent(true)` + alpha-0 clear, `visible(false)`; reveal на первом кадре не виден ничему (нет рамки, нет пикселей). UI настроек остаётся в child viewport (v3), подавление root сохраняется как страховка.
- **v5 — флеш при повторном запуске: консольное окно, не окно настроек (отчёт пользователя).** Второй инстанс выходит до создания GUI (гвард берётся до трея/хоткеев/окна, main.rs:449–468), поэтому окно в этом пути не появляется вообще. Флеш даёт `tasklist`-проб живости pid (`instance.rs:169–178`): дочерний console-процесс, запущенный из GUI-subsystem процесса (`#![windows_subsystem = "windows"]`, main.rs:70), получает собственное консольное окно — чёрный флеш на мгновение. Правка: `std::os::windows::process::CommandExt::creation_flags(CREATE_NO_WINDOW)` на `tasklist` (safe std API, без новых зависимостей, без `unsafe`). Остальные runtime-спавны (`current_exe()` в restart/update) — сам GUI-subsystem бинарь, консоль не создаёт.

## Constraints

- Rust edition 2024, bin-only root crate; `#![forbid(unsafe_code)]`; один winit `EventLoop` на процесс (обвязка overlay/toast/tray внутри create-closure `gui::run`).
- Один модуль = один файл; юнит-тесты приватных internals — sibling `config.tests.rs`; e2e без TDD.
- Gates: `./scripts/check.sh` после батчей правок (с `SKIP_E2E=1` для коммит-гейта), `./scripts/check_full.sh` на границе стадии; `./cargo.sh` — кэши в `./.cache/`.
- Новые зависимости не нужны.
